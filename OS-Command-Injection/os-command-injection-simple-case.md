### Step 1 - Configure Burp Suite and Access the Lab

Open the PortSwigger lab in Firefox and ensure Burp Suite is running.

Before interacting with the application, configure Burp Suite's **HTTP History** filters to reduce unnecessary traffic.

Enable only the request types relevant to the assessment and hide common static resources such as images, CSS, fonts, and SVG files.

Reload the page.

The HTTP History now contains only the requests generated by the target application, making it easier to identify the endpoint that will be tested.

### Why?

The objective of this step is to prepare Burp Suite for testing.

Filtering unnecessary traffic reduces noise and allows penetration testers to focus only on requests generated by the application's functionality.

This makes identifying potentially vulnerable endpoints significantly easier.

### Step 2 - Identify the Request That Checks Product Stock

Navigate to any product page and scroll to the **Check stock** feature.

Click **Check stock**.

Burp Suite captures the generated request in **HTTP History**.

Locate the following request:

```http
POST /product/stock HTTP/2
```

This request is responsible for checking product availability and accepts user-controlled input.

At this stage, no modifications are made to the request. The objective is to identify the endpoint that will be tested for OS Command Injection.

https://github.com/user-attachments/assets/1dca4771-5bf2-4277-8a47-7f9c659f39b7

### Why?

Before attempting exploitation, it is important to identify which functionality processes user-supplied input.

The **Check stock** feature sends a POST request containing parameters processed by the backend application.

Because stock-checking functionality often executes operating system commands or external utilities, it represents a common target for **OS Command Injection** vulnerabilities.

---

### Step 3 - Inject an Operating System Command

Right-click the `POST /product/stock` request and select **Send to Repeater**.

Locate the following request body:

```text
productId=1&storeId=1
```

Append the following payload to the **storeId** parameter:

```text
;whoami;
```

Highlight the injected payload and press **Ctrl + U** to URL-encode it.

The request body becomes:

```text
productId=1&storeId=1%3Bwhoami%3B
```
<img width="613" height="560" alt="image" src="https://github.com/user-attachments/assets/d83722a5-69a1-4c95-b1f0-5af998c16315" />

Click **Send**.

The response now contains both the product stock value and the output of the injected command.


### Why?

The objective of this step is to determine whether the application incorporates user-controlled input into an operating system command.

If the input is executed by the operating system, the injected `whoami` command is executed alongside the application's intended command.

Receiving the command output confirms the presence of an **OS Command Injection** vulnerability.

---

### Step 4 - Verify Successful Command Execution

Inspect the server's response after sending the modified request.

For example:

```text
62
peter-cvlqel
```

The value `62` represents the legitimate stock quantity.

The username `peter-cvlqel` is the output of the injected `whoami` command, confirming that the operating system executed the attacker-controlled command.

At this point, the lab is solved because arbitrary operating system commands can be executed through the vulnerable parameter.

### Why?

The `whoami` command is commonly used during penetration tests because it safely verifies command execution without modifying the target system.

Receiving both the stock value and the username demonstrates that the application executed its original command and then executed the injected command, confirming successful **OS Command Injection**.

## Execution Flow

```text
Browser
      │
      ▼
POST /product/stock
      │
      ▼
Application builds an OS command
      │
      ▼
Shell interprets ';'
      │
      ▼
whoami executes
      │
      ▼
Output returned to the browser

```

### Why does this work?

The application incorporates user-controlled input directly into an operating system command without properly validating or sanitizing it.

Because the shell interprets the semicolon (`;`) as a command separator, it executes both the application's intended command and the attacker's injected `whoami` command.

The output of the injected command is then returned in the HTTP response, confirming that the application is vulnerable to **OS Command Injection**.

The output is returned in the HTTP response, confirming successful **OS Command Injection**.
## What I Learned

- Burp Repeater allows requests to be modified and resent.
- `whoami` safely verifies command execution.
- The semicolon (`;`) is a shell command separator.
- URL encoding preserves special characters in HTTP requests.
- OS Command Injection can lead directly to Remote Code Execution (RCE).

## Impact

Successful exploitation allows an attacker to:

- Execute arbitrary operating system commands.
- Read sensitive files.
- Download additional payloads.
- Potentially gain full control of the server.

## Mitigation

To prevent this vulnerability:

- Avoid executing shell commands whenever possible.
- Use native APIs instead of system commands.
- Validate input using allowlists.
- Reject shell metacharacters such as `;`, `&`, and `|`.
- Apply the principle of least privilege.
